# 工程文档与 ADR

## 核心原则

代码说明“实现了什么”，文档应补充“为什么这样实现、受哪些约束、放弃了哪些方案”。不要用文档复述显而易见的代码。

## 适用范围

以下情况必须评估并更新文档：

- 做出重要或难以逆转的架构决策
- 选择框架、依赖、数据模型、鉴权或基础设施方案
- 新增或变更公共 API、共享契约和持久化格式
- 交付改变用户行为或跨模块流程的功能
- 改变项目结构、开发命令、部署或运维方式
- 同一背景或约束被反复解释
- 发现未来开发者或 Agent 容易重复踩坑的隐含规则

纯内部实现调整、临时代码和代码本身已清晰表达的行为，不需要额外文档。

## 修改前先查现有约定

创建或更新文档前，搜索：

- `README*`、`CONTRIBUTING*`、`CHANGELOG*`
- `docs/**` 中的架构、API、运行手册和 ADR
- `.trae/skills/**` 中的项目约束
- `.adr-dir`、ADR 工具配置或 CI 校验
- 邻近模块的注释、类型和接口文档

已有约定优先于本 Skill 的默认值。必须匹配现有的目录、编号、文件名、标题和状态格式，不能平行引入第二套体系。证据冲突时先说明冲突并请求确认。

## Architecture Decision Record

### 需要 ADR 的情况

当决策满足以下任一条件时创建 ADR：

- 未来修改成本高
- 影响多个模块、团队或外部调用方
- 存在多个可行方案且有明确取舍
- 涉及安全、数据一致性、兼容性、性能或成本
- 旧决策被替代或废弃

### 默认位置和命名

仅当项目中没有既有约定时，使用：

```text
docs/decisions/ADR-001-short-title.md
```

继续现有编号，不得重启序列。标题应描述决策，而不是任务名。

### 默认模板

```markdown
# ADR-001: 决策标题

## Status
Proposed | Accepted | Superseded by ADR-XXX | Deprecated

## Date
YYYY-MM-DD

## Context
需要解决的问题、约束、目标和决策驱动因素。

## Decision
选择了什么，以及适用边界。

## Alternatives Considered
候选方案、优缺点和拒绝原因。

## Consequences
正面结果、代价、风险、迁移与后续工作。
```

ADR 生命周期：

```text
Proposed -> Accepted -> Superseded / Deprecated
```

不要删除旧 ADR。决策变化时创建新 ADR，并通过状态和链接建立替代关系。

## API 与契约文档

新增或修改公共 API 时，至少记录：

- 用途和调用场景
- 鉴权与权限要求
- 输入字段、约束和默认值
- 成功输出和状态码
- 业务错误、错误码和重试语义
- 幂等性、兼容性和版本策略
- 最小可运行示例

TypeScript 公共函数优先使用类型表达结构，只对不明显的约束、异常和副作用补充 JSDoc。REST API 若已有 OpenAPI 体系，应同步更新其单一真源。

## 行内注释

注释解释原因、约束和非直觉行为：

```typescript
// 共享用户只能提交布局字段，避免签名 URL 等运行时数据触发图状态校验。
const layoutOnlyGraph = extractLayout(graph)
```

禁止：

- 复述下一行代码
- 保留注释掉的旧实现
- 用长期 TODO 代替任务或实现
- 写下会快速过期的具体实现细节

已在 ADR 或设计文档中解释的复杂约束，可在代码旁添加短注释并链接到该文档。

## README 与运行文档

当相关事实变化时同步更新：

- 项目用途和架构概览
- 环境变量与依赖前置条件
- 安装、开发、测试、构建和部署命令
- 数据迁移、回滚和故障处理步骤
- 新模块入口和关键文档链接

命令必须来自仓库实际脚本，并在可能时执行验证。不要复制未经验证的通用命令。

## 变更记录

用户可见功能、兼容性变化和重要修复应按项目现有格式更新 changelog 或发布说明，说明：

- 新增了什么
- 修复了什么
- 改变了什么
- 是否需要迁移或人工操作

## 文档与代码同步流程

1. 识别本次变更影响的使用者和长期约束。
2. 搜索现有文档真源，避免重复和冲突。
3. 在实现过程中同步修改文档，不延后到“以后补”。
4. 检查路径、命令、接口、字段和链接是否真实存在。
5. 用 `git diff` 联合审查代码与文档，确认两者描述一致。

## 完成检查

- [ ] 重要架构决策已有 ADR，包含背景、方案和后果
- [ ] 旧 ADR 未被删除，替代关系清晰
- [ ] 公共 API 的输入、输出、错误和权限已记录
- [ ] README 和运行命令与仓库当前状态一致
- [ ] 用户可见变化已进入项目采用的变更记录
- [ ] 注释解释原因而非复述代码
- [ ] 文档中的路径、命令和链接已验证
- [ ] `.trae/skills` 等 Agent 规则与新约束一致
